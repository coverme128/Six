# P2.1 Live AI and P3-A Staging Runbook

Status: `LOCAL_LIVE_PROVIDER_VERIFIED_STAGING_PENDING`

This runbook covers only controlled staging readiness. It does not authorize public beta, production, login, payments, CMS, advanced rules, review rules, or precise timing.

## Preconditions

- `DEEPSEEK_API_KEY` exists only in a secure local shell or deployment secret store.
- `.env.example` contains placeholders only and no real key.
- `AI_MODEL`, `AI_TIMEOUT_MS`, and `AI_MAX_OUTPUT_TOKENS` are explicitly configured for staging.
- Staging sets `APP_ENV=staging` and `NODE_ENV=production`.
- `/internal/status` is protected by `INTERNAL_STATUS_TOKEN` or deployment platform basic auth.

## Live Smoke

Run:

```bash
pnpm run smoke:ai:live
```

The command skips when the selected provider key is not present. A completed P2.1 smoke runs five Liuyao cases. With DeepSeek, each successful case reports `reportSource = DEEPSEEK_LIVE`, passes `AI_REPORT_V1`, fact fidelity, evidence-reference, timing, safety, and plain-language validation, and avoids invented evidence or timing.

Smoke logs may include case id, report type, provider, model, success flags, fallback flag, latency, token usage, error code, and question digest. They must not include the full question, prompt, model output, API key, or user private content.

## Staging Checks

Required endpoints:

```text
GET /health
GET /ready
GET /internal/status
```

Expected checks:

- `/health` returns only process liveness.
- `/ready` confirms CORE_V1, CAL_STD_V1, AI provider configuration, and content readability without secrets.
- `/internal/status` shows version, commit, environment, engine/calendar/rule profile, AI provider/model, prompt/schema versions, startup time, and aggregate metrics.

Run browser regression against the staging URL after deployment:

```bash
pnpm run test:e2e
```

Staging E2E must include Liuyao coin, Liuyao manual, AI success, AI fallback, report refresh restore, local history, mobile 360/390/430, health, and readiness checks. The AI success path must confirm `DEEPSEEK_LIVE`; fallback must confirm `DETERMINISTIC_FALLBACK`.

## Rate and Cost Controls

Configure staging:

```text
AI_RATE_LIMIT_WINDOW_MS
AI_RATE_LIMIT_MAX
DIVINATION_RATE_LIMIT_MAX
AI_CONCURRENCY_MAX
AI_DAILY_BUDGET_LIMIT
```

When rate limits are hit, the API returns a public rate-limit error. When the AI daily budget or concurrency limit is hit, real provider calls are skipped and the user still receives a deterministic fallback report.

## Rollback

1. Redeploy the previous known-good commit or saved deployment version.
2. Keep `DEEPSEEK_API_KEY` and other secrets in the secret store; do not copy them into source files or logs.
3. If AI cost or schema failures are the incident trigger, temporarily set `AI_DAILY_BUDGET_LIMIT=0` or disable the live provider to force deterministic fallback.
4. Verify `/health` and `/ready`.
5. Run `npm test` and the smoke command in skipped or live mode as appropriate.
6. Confirm existing local history reports still open and that new reports can fall back without page failure.

## Promotion Gate

Do not mark `LIVE_AI_PROVIDER_VERIFIED` until the real smoke completes without relying on deterministic fallback. Do not mark `STAGING_DEPLOYMENT_READY` until live smoke has passed and a HTTPS staging URL has passed health, readiness, E2E, and live AI checks.
